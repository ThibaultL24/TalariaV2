# SNAC Lot 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Persist a sourced SNAC identity, its typed relations, and its archival collections for one Talaria person, then expose them on two read APIs, without creating a canonical event.

**Architecture:** Pure functions decide alignment, assertion keys, and document qualification. A single SQLx transaction persists a validated harvest. `entity_identity_links.status` is the only alignment authority. Relations become non-current only after that validated harvest commits.

**Tech Stack:** Rust workspace, SQLx 0.8 (`PgExecutor`), PostgreSQL migrations `043`–`045`, Axum routes, fixtures under `crates/talaria-sources/tests/fixtures/snac/`.

**Spec:** `docs/superpowers/specs/2026-10-18-snac-relations-design.md`

## Global Constraints

- No canonical event, no place of presence, no write to `claims`, `soft_claims`, `quality_claims`, `canonical_events`, or `document_fragments`.
- No frontend. No lot 2 text extraction.
- Do not invent a Talaria entity for a correspondent. Target constellations stay `stub`.
- Do not freeze JSON paths until task 1 has saved real `search` and `read` bodies.

### Lock 1 — one SQLx transaction

`persist_snac_harvest` starts one `pool.begin()`. Every write, including contribution replacement, runs on `&mut tx`. A `&PgPool` parameter is forbidden inside that function.

`&PgPool` implements `sqlx::PgExecutor`, but a helper that only accepts `&PgPool` opens its own connection and commits outside the transaction. These four functions change from `pool: &PgPool` to a generic executor:

- `upsert_corpus_document`
- `replace_document_identifiers`
- `replace_document_contributions`
- `upsert_entity_document_link`

```rust
use sqlx::PgExecutor;

pub async fn replace_document_contributions<'c, E>(
    executor: E,
    corpus_document_id: Uuid,
    rows: &[ContributionInsert],
) -> anyhow::Result<()>
where
    E: PgExecutor<'c>,
{
    sqlx::query("DELETE FROM document_contributions WHERE corpus_document_id = $1")
        .bind(corpus_document_id)
        .execute(executor)
        .await?;
    // each INSERT uses the same executor value; split the function so the
    // executor is borrowed per statement, not stored across awaits of another pool
    Ok(())
}
```

The real function keeps the existing loop. Each `.execute` borrows the executor for one statement. Call sites that already pass `&pool` keep compiling. `persist_snac_harvest` passes `&mut *tx`.

The advisory lock is the first statement on that same transaction:

```rust
sqlx::query("SELECT pg_advisory_xact_lock($1)")
    .bind(advisory_key(&entity_id))
    .execute(&mut *tx)
    .await?;
```

`advisory_key` copies the first eight bytes of the UUID, little-endian, into an `i64`. It only serializes harvests. The unique indexes decide identity.

### Lock 2 — a harvest is complete only when validation succeeds

HTTP 200 is not enough. `read_constellation` returns `Result<ValidatedHarvest, HarvestReject>`.

`HarvestReject` variants: `Http`, `RateLimited`, `BodyTooLarge` (body longer than 2_000_000 bytes), `InvalidJson`, `NotUtf8`, `Split` (zero or more than one constellation), `Withdrawn`, `BlockingParse` (the subject ARK is missing or a relation/resource entry is not an object).

An unknown relation type is not a reject. It becomes `predicate = unmapped`, `validation_status = needs_review`. An unknown resource role is not a reject. It is counted in `snac_resources_role_unmapped` and stored without an `entity_document_links` row.

`retire_absent_relations` and `retire_absent_holdings` run only when all of these are true:

1. the value is `Ok(ValidatedHarvest)`;
2. `record_status == complete`;
3. the identity decision for this entity is a single `aligned`;
4. the transaction has not returned an error.

Any `HarvestReject`, any panic converted to `Err`, and any SQL error rolls back. Existing `is_current` rows stay current.

### Lock 3 — `entity_identity_links` is the only alignment authority

`entities.authority_ids.snac_ark` may be written after a final status `aligned`. No function may read that key to decide `aligned`. Lookup SQL joins `entity_identity_links` where `status = 'aligned'`. A test inserts `authority_ids = {"snac_ark":"ark:/99166/w6example"}` with no link row and asserts both API lists are empty.

### Lock 4 — assertion key `snac-assertion-key:v1`

Constant `ASSERTION_KEY_VERSION: &str = "snac-assertion-key:v1"`. Do not change it without a migration that rewrites keys.

Whitespace for text fields: trim, then replace every Unicode whitespace run with one U+0020. Case stays as received. Empty after that treatment is absent.

ARK: strip one prefix `http://n2t.net/`, `https://n2t.net/`, `http://snaccooperative.org/`, `https://snaccooperative.org/`, `http://www.snaccooperative.org/`, or `https://www.snaccooperative.org/`. The remainder must start with `ark:/`. ASCII lowercase. Anything else is `None`.

Dates in the key use this object, keys in this order, omitting empty optionals: `kind`, `precision`, `surface`, `start`, `end`. `kind` is only `exact`, `range`, `approx`, or `unknown`. `precision` is only `day`, `month`, or `year`, and only when `kind != unknown`. Otherwise the date object is `{"kind":"unknown","surface":"<original>"}` or `{"kind":"unknown"}` when the surface is absent.

Canonical assertion JSON, compact, keys sorted by `BTreeMap`:

```json
{"assertion_text":null,"dates":{"kind":"unknown"},"object_ark":"ark:/99166/w6object","source_predicate":"correspondedWith","subject_ark":"ark:/99166/w6subject","v":"snac-assertion-key:v1"}
```

`assertion_text` is always present: the normalized string, or `null` when absent. `source_predicate` is trimmed but not case-folded.

If the SNAC relation id trims to a non-empty string, `source_assertion_key = "snac:" + that id`. The hash is not the key. If the id is absent, `source_assertion_key = "sha256:" + hex(sha256(canonical_json))` using lowercase hex.

`content_hash` on the relation is `hex(sha256(canonical_json))` in both cases. Same key and same hash: update `retrieved_at` only. Same key and different hash: set the current row `is_current = false`, `superseded_at = now()`, insert the new row.

The snapshot hash is different: SHA-256 of the raw UTF-8 response body, stored in `document_snapshots.content_hash`. `document_snapshots.text` is that raw body. `revision_id` is the SNAC version string. Do not re-serialize the body before hashing it.
